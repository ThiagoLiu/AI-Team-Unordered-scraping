## 一、总体路线

用户选定的组合：

1. **手写一个 agent**（第 1～4 步）：从零理解 API → tool use → agent 循环 → skill 机制
2. **用 Claude 看相机图像做抓取失败诊断**：最快把"AI 用进产品"
3. **每周一个小实验**，逐个上手 Claude Code 的真实功能
4. 主线：工件配方化 → 离线回放数据集 → 新工件导入 skill → 打包成 plugin

核心理念（已向用户讲过）：
- 最值钱的能力是**给 AI 提供上下文、建立验证闭环、判断 AI 的能力边界**，工具名会变，这些不会
- 多 agent 不要追求"模拟团队"，按"独立、可并行、只回报结论"来拆分
- skill 至少在换过 2 个工件之后再封装
- AI 不直接控制真实机器人
- Python 做主力（大脑：视觉、AI、流程编排），C++ 只做实时控制（小脑）

## 二、各步骤进度

### 第 1 步：认识大模型 API —— 已完成

文件：`step1_hello_api.py`（实验一～五）

已掌握的概念：
1. 调用 API = 调用函数：发送 `messages`，返回内容块列表
2. 模型没有记忆：它能用的只有这一次发过去的内容，"对话"是每次重发历史
3. 内容块类型：`thinking`、`text`（下一步还有 `tool_use`）
4. `max_tokens` 包括思考的消耗；要检查 `stop_reason`（`end_turn` / `max_tokens` / `tool_use`）
5. system 提示是 CLAUDE.md 的原型：上下文让输出对上项目约定，也会限定模型思考范围；没写到的地方模型会自己假设（实验四默认了眼在手外，没提眼在手上的情况）

过程中遇到的问题（都已当作教学点讲过）：
- `ModuleNotFoundError: anthropic` → 多个 Python 环境，讲了 `python -m pip`
- `'ThinkingBlock' object has no attribute 'text'` → 讲了内容块列表
- 实验四只有 thinking 没有回答 → `max_tokens=300` 被思考耗尽
- 文件被旧版本覆盖 → 讲了"核对实际运行的是不是最新代码"和 git 的必要性

用户的检验题回答：
- Q1 模型为什么答不出"刚才问了什么"：答"没有上下文"✔（补充：不是忘了，是根本没收到）
- Q2 长对话为什么会忽略早期约定：答"超出上下文窗口" ✔ 一半（补充：长上下文注意力稀释、工具会压缩早期历史；解决：放进 system/CLAUDE.md、新开对话带摘要）
- Q3 删掉 system 会怎样：起初不理解，通过实验四/五对比理解了，用户总结为"一个有约束，一个没约束"，已补充三个细节

用户提出的疑问及解答：
- "step1 算 agent 吗？" → 不算。agent = 模型 + 工具 + 循环，关键是**由模型决定下一步**
- "system 是限定和记忆吗？" → 是限定；"记忆"本质是每次发送的全部内容
- "里面有 skill 吗？" → 没有。skill = 按需加载的操作说明（SKILL.md），平时只加载描述；"去取"需要工具，所以 skill 建立在 agent 之上。比喻：CLAUDE.md 是车间墙上的安全规程，skill 是柜子里贴了标签的作业指导书

### 第 2 步：Tool use —— 已运行成功，等用户回答两道追问后进入第 3 步

文件：`step2_tool_use.py`

内容：
- 第一部分：建 `.venv` 虚拟环境、`requirements.txt`、git 初始化（用户换了新电脑，需要重新做）
- 第二部分：工具 `camera_to_base(x_mm, y_mm, z_mm)`，示例 `T_BASE_CAM` 为相机在基座上方 1200 mm、绕 X 轴转 180°、X 偏移 500 mm
  - 实验一：不需要工具的问题 → 模型不调用工具
  - 实验二：需要工具的问题（输入单位是米）→ `stop_reason=tool_use`，观察模型是否把 0.1 m 换算成 100 mm 作为参数
  - 实验三：执行工具、用 `tool_result` + `tool_use_id` 发回 → 期望结果 **(600, -200, 700) mm**

已讲解的核心概念：
1. 工具定义 = 给模型的使用说明（名字 + description + input_schema），模型看不到 Python 代码
2. 模型只"请求"不执行，执行的是你的代码 → 每个动作都经过你的代码，可以检查/记录/拒绝（hooks 的原理）
3. `tool_use_id` 用来对应请求和结果

运行情况（2026-11-18，新电脑）：
- 环境问题：`python` 指向 WindowsApps 下的应用商店占位程序（退出码 49），真正的 Python 3.14 要用 `py` 调用 → 讲了"先确认运行的是哪个 Python"，用 `py -m venv .venv` 建环境
- 结果与预期一致：实验一没有调用工具；实验二 `stop_reason=tool_use`，模型把 0.1 m 换算成 100 mm，并且**在 tool_use 块前面输出了一个 text 块**（已借此讲了为什么要遍历 content）；实验三得到 (600, -200, 700) mm

检验题及用户回答：
1. 实验二结束时 `camera_to_base` 执行了几次、谁执行的？→ 答"0 次，不知道怎么执行的"。0 次 ✔；已讲第 121 行由你的代码执行，模型在服务器上碰不到本地函数
2. 为什么不让模型自己算？→ 答"就是模型算的" ❌（误以为结果是模型算的）。已对照输出顺序纠正，并讲了三个理由：**模型根本没有 T_BASE_CAM 数据**（最根本）、确定性/精度、可检查可记录（hooks 原理）
3. 先 A 后 B 现有代码能处理吗？→ 答"不会"。已讲现有代码只多问一轮就结束，并给出 while 循环伪代码，引出第 3 步

**待用户回答的追问（用来巩固 Q1/Q2，并铺垫第 3 步）：**
1. 把第 121 行改成返回 (0,0,0)，模型最终会答什么？说明什么？（要点：模型直接相信工具结果、不会自己验算 → 工具的正确性要由你负责）
2. 循环在什么条件下结束？如果模型一直请求工具会怎样？加什么保护？（要点：`stop_reason != "tool_use"` 时结束；需要最大轮数限制，防止死循环和费用失控）
